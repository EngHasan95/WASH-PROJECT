# تصور مشروع إدارة البلاغات — مؤسسة المياه والصرف الصحي، فرع مأرب

الحالة: مقترح للاتفاق، قبل بدء البرمجة.
المرجع: approved-requirements-ar.md، نسخة مطابقة لوثيقة المستخدم، مع التعديلات اللاحقة في accepted-updates-ar.md التي تقدم عند التعارض.

## حدود التفويض

المطلوب حاليًا ترتيب بيئة العمل والتصور والمخرجات. لا يبدأ تنفيذ التطبيق قبل اتفاق المستخدم وقوله «انطلق». بعد بدء التنفيذ، تتوقف كل مرحلة عند تسليم جزء قابل للاختبار، ولا تبدأ المرحلة التالية قبل اختبار المستخدم واعتماده. لا تُربط المراحل بعدد أيام.

## النتيجة المقترحة

تطبيق ويب عربي RTL واحد يعمل على الكمبيوتر ومتصفح Android، لإدارة البلاغ من تسجيل المواطن بنفسه والتوجيه الآلي للمختص إلى الإغلاق النهائي بواسطة مدير الشؤون الفنية. يحتفظ بالبلاغ وسجل إجراءاته ومرفقاته، ويتيح البحث والمتابعة والتقارير. يستطيع المواطن متابعة حالة بلاغه، ويستطيع الفني الوصول إلى البلاغات المسندة إليه وبدء العمل وتسجيل النتيجة وإرسالها للمراجعة.

الأدوار الأساسية: موظف تسجيل البلاغات، مدير الشؤون الفنية، الفني. مدير الشؤون الفنية وحده يملك الإغلاق النهائي وفق المتطلبات. المستخدمون الفنيون المتوقعون 21؛ تُطلب بياناتهم الفعلية عند الحاجة، ولا تُختلق بيانات موظفين.

بوابة المواطنين للتسجيل والمتابعة والتوجيه التلقائي أصبحت ضمن النطاق بتصحيح المستخدم. اعتمد المستخدم التوجيه إلى مسؤول القسم حسب نوع البلاغ، ثم إسناده إلى الفني بواسطة المسؤول. لا يفترض تكامل رسائل WhatsApp.

## تقنية مقترحة، تحتاج الاتفاق

- Python وDjango لتطبيق موحد يضم تسجيل الدخول والصلاحيات ومنطق العمل والصفحات.
- PostgreSQL لقاعدة البيانات في التطوير والنسخة التشغيلية، لتقليل اختلاف السلوك بينهما.
- صفحات Django وHTML/CSS/JavaScript بواجهة عربية متجاوبة؛ دون فصل واجهة وخادم في مشروعين مستقلين.
- تشغيل الموارد الأساسية محليًا ضمن التطبيق، وتثبيت إصدارات التبعيات بعد التحقق من توافقها عند بدء المرحلة الأولى.
- حفظ المرفقات في مساحة خاصة مع التحقق من صلاحيات تنزيلها. اختيار التخزين التشغيلي النهائي مع الاستضافة.

هذه البرمجيات متاحة كمشاريع مفتوحة المصدر؛ لم تُختَر استضافة خارجية ولم تُتحقَّق أسعارها أو حدودها. لا تعني مجانية البرمجيات ضمان مجانية الاستضافة أو التخزين أو النسخ الاحتياطية. الأولوية لخدمات مجانية موثقة عند الحاجة دون الاشتراك في خدمات مدفوعة.

## تنظيم العمل

المستودع الحالي: /workspace/WASH-PROJECT، ويحتوي عند إعداد هذا التصور على README.md فقط. تم التحقق من تطابق الالتزام الحالي مع main ومن وصول Git للقراءة ومن نظافة الملفات.

عند اعتماد التقنية وبدء المرحلة الأولى، تُنشأ بيئة Python معزولة وتُثبَّت التبعيات المحددة، وتُجهَّز قاعدة تطوير ببيانات تجريبية، وتُختبَر خطوات التشغيل. تُحفظ تعليمات التثبيت والتشغيل المطلوبة في إعدادات البيئة السحابية بعد تجربتها، وفق مهارة cloud-environment-onboarding:setup.

كل مهمة سحابية معزولة أصلًا؛ يُستخدم المستودع الموجود، ولا يُنشأ Git worktree إلا بطلب المستخدم. لا تُضمَّن أسرار أو بيانات مواطنين حقيقية في ملفات المشروع أو سجل Git. لا تُغيَّر ملفات التطبيق والتبعيات المقفلة بسبب إعداد البيئة؛ تغييرات البرمجة تتم ضمن المرحلة التي يعتمدها المستخدم.

Codex يتولى أوامر التطوير وإدارة التعديلات واختبارات كل مرحلة. المستخدم يختبر الجزء المسلَّم ويعتمد الانتقال. قد يتطلب النشر أن يقوم المستخدم بإنشاء حساب أو إكمال تحقق لدى الاستضافة؛ يُطلب الإجراء المحدد عند الحاجة دون طلب كلمات مرور أو أسرار في المحادثة.

## دورة البلاغ

تسجيل المواطن ورقم فريد ← توجيه تلقائي لمسؤول القسم حسب نوع البلاغ ← مراجعة المسؤول وإسناده إلى الفني ← بدء العمل ← تسجيل التنفيذ والصور عند الحاجة ← انتظار مراجعة التنفيذ ← إغلاق أو إعادة للمتابعة. يستطيع المواطن متابعة حالة بلاغه.

تُبنى الصلاحيات وسجل الأحداث مع الأجزاء التي تُحدث تغييرات؛ تُعرض واجهة السجل الكاملة في المرحلة السادسة. نتيجة التواصل مع المواطن اختيارية. لا يفرض تحديد الموقع الجغرافي أو رقم الاشتراك أو رقم العداد لتسجيل كل بلاغ.

تُحفظ أنواع البلاغات السبعة وقائمة الأحياء السبعة والثلاثين من المرجع بنصها المعتمد، مع إدخال نوع أو حي إضافي عند اختيار «أخرى». تشمل المنظومة بلاغات الفواتير والاشتراكات. لا يُفترض تحويل صلاحية إغلاقها إلى جهة أخرى.

## مراحل التنفيذ ومعيار التسليم

1. الأساس والدخول والصلاحيات: نسخة تعمل بصفحات عربية متجاوبة وحسابات تجريبية للأدوار الثلاثة؛ اختبار السماح والمنع لكل دور. يمكن للمستخدم تسجيل الدخول وتجربة واجهته.
2. تسجيل المواطن للبلاغ: النموذج والأنواع والأحياء والرقم الفريد والحقول الاختيارية والصور؛ حفظ بلاغ تجريبي وإعادة فتحه للتأكد من استمرار البيانات.
3. القائمة والبحث والتفاصيل ومتابعة المواطن: العثور على البلاغ وفتح بياناته ومتابعة حالته؛ اختبار البحث والفلاتر الأساسية وحدود الاطلاع.
4. التوجيه التلقائي والمراجعة والإسناد: يوجه البلاغ إلى مسؤول القسم حسب نوعه، ثم يراجعه المسؤول ويسنده إلى الفني؛ يظهر البلاغ في حساب المسؤول والفني المحدد ويُسجل وقت الإسناد والمسؤول.
5. واجهة الفني: بدء العمل وتسجيل التنفيذ والملاحظات والصور وإرساله للمراجعة؛ اختبارها بحجم شاشة هاتف ومنع الإغلاق النهائي عن الفني.
6. مراجعة التنفيذ والإغلاق والإعادة والسجل: المدير يغلق أو يعيد البلاغ؛ اختبار المسار الكامل وسجل الإجراءات والتواصل الاختياري.
7. لوحة الإدارة والتقارير: الأعداد والتوزيعات والفلاتر والتصدير البسيط؛ مطابقة التقارير للبيانات التجريبية. تعتمد حسابات التأخر على مدد يحددها المستخدم عند هذه المرحلة.
8. النسخة التشغيلية: مراجعة الهاتف والصلاحيات والملفات والاستقرار، واختيار الاستضافة بعد التحقق من شروطها، وتجربة النسخ الاحتياطي والاستعادة، وتسليم رابط HTTPS صالح للاستخدام بعد نجاح النشر.

بعد كل مرحلة: اختبارات Codex، تسليم واضح مع طريقة تجربة، اختبار المستخدم، معالجة ملاحظاته ضمن الجزء المعني، فحص عدم تراجع الوظائف المعتمدة، ثم انتظار اعتماده. لا يبدأ العمل من جديد عند ورود الملاحظات.

## المخرجات عند اكتمال المراحل

- رابط نظام ويب عربي منشور، قابل للاستخدام من الكمبيوتر وهاتف Android.
- ملفات المصدر محفوظة في WASH-PROJECT، وتوثيق الإعداد والتشغيل.
- قاعدة بيانات ومرفقات مستمرة التخزين، وصلاحيات المستخدمين وسجل البلاغات.
- دورة بلاغ مكتملة وتقارير وتصدير بسيط، وإرشادات قصيرة للاستخدام والنسخ الاحتياطي والاستعادة.

رابط الاختبار لكل مرحلة يعتمد على وسيلة العرض المتاحة. بيئة onboarding الحالية لا تدعم تقديم روابط localhost للمستخدم؛ الطلبات المحلية تستخدم للتحقق الداخلي. يُجهَّز رابط اختبار متاح للمستخدم عند التنفيذ ولا يُدَّعى توفره قبل اختباره.

## قرارات تُحسم عند الحاجة

طلب المستخدم لاحقًا وحدة «المخالفات الميدانية» للفنيين داخل النظام نفسه؛ وصفها في field-violations-ar.md ومسارها المعتمد في accepted-updates-ar.md. تحتاج مرحلة مستقلة يتفق على موضعها في التسلسل قبل التنفيذ. لا تنتقل صلاحية إغلاق بلاغات المواطنين تلقائيًا إلى هذه الوحدة؛ صلاحيات تأكيد السداد وإغلاق المخالفة وسياسة الغرامات تحتاج التحديد عند تنفيذها.

- مدد اعتبار البلاغ متأخرًا؛ لا تُختلق سياسة زمنية.
- أسماء المستخدمين وبياناتهم المطلوبة لتجهيز الحسابات الفعلية.
- الاستضافة والتخزين وحدود المجانية ومتطلبات الحساب والنشر.
- قواعد صلاحيات إضافية أو تعارض حقيقي يظهر أثناء تنفيذ جزء محدد.

الأسئلة المؤجلة لا تمنع الاتفاق على التصور أو تجهيز المرحلة الأولى بعد الإذن.
