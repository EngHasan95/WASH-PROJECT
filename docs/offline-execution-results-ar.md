# حفظ نتيجة التنفيذ وصورها قبل الرفع

نتيجة المعالجة متاحة للفني المسند إليه البلاغ الفني، وللمختص المسند إليه البلاغ المالي، عندما تكون المهمة «قيد المعالجة». المدير الفني يراجع النتيجة ويعيدها أو يغلق البلاغ؛ إرسال النتيجة لا يغلقه.

عند فتح المهمة بالحساب المسؤول أثناء الاتصال، تُجهز على الجهاز بطاقة محدودة تحتوي رقم المهمة ونوعها وعنوانها ومعرّف جولة العمل، دون اسم المستفيد أو هاتفه أو الصور الواردة منه. تظهر إفادة ذلك في نموذج النتيجة المعتاد. لم تُضف نافذة أو قائمة منفصلة للعمل دون اتصال.

زر «إرسال النتيجة للمراجعة» يحفظ النص وحتى ثلاث صور في IndexedDB أولًا، ثم يحاول الرفع. يمكن إعادة تحميل رابط المهمة نفسه عند انقطاع الاتصال ورؤية النتائج والصور المحفوظة لهذا الحساب. يلزم فتح المهمة وبدء معالجتها أثناء الاتصال قبل تجهيز حفظ نتيجتها دون اتصال. قد يلزم إبقاء التطبيق مفتوحًا أو إعادة فتحه للمزامنة؛ لا يوجد ضمان رفع تلقائي عندما يغلق المتصفح.

المزامنة تتحقق من تطابق الحساب المحلي مع جلسة الخادم، وتستخدم معرّف نتيجة ثابتًا. يعيد الخادم نفس إيصال الحفظ عند تكرار الطلب، حتى بعد الإغلاق، دون إنشاء حدث أو صورة إضافية. إذا تغير إسناد المهمة أو جولتها أو حالتها قبل الرفع، يحتفظ الجهاز بالنص والصور ويعرض ضرورة المراجعة مع المسؤول. لا يعيد النظام إسنادها أو يتجاوز الحالة تلقائيًا.

الصور تُفحص وتُحوّل إلى JPEG دون معلومات EXIF قبل تخزينها الخاص. الوصول عبر واجهة تتحقق من نطاق الموظف الحالي أو المدير، مع `no-store, private`. بوابة المستفيدين لا تعرض نتائج العمل الداخلية ولا صور التنفيذ. تحتوي CacheStorage فقط القالب العام والملفات الثابتة؛ لا تُخزن صفحات الحساب أو الجلسة أو التوكنات أو الاستجابات الخاصة فيها.

أثبت الفحص 12 اختبار Django للرفع والتكرار والصلاحيات والتعارض والصور والاسترجاع بعد فشل التخزين، وخمس مجموعات متصفح حقيقية تشمل الحفظ دون اتصال وإعادة التحميل والمزامنة وإعادة الطلب وتغيير الإسناد والعزل بين المستفيد والموظف وفحص CacheStorage. الأدلة في `test-results/execution-offline-validation/`. هذه اختبارات سحابية على Linux؛ لا تثبت تنفيذ ملفات Windows الفعلية.
